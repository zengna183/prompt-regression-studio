# 安全部署指南

这份文档说明 Prompt Regression Studio 当前已经防住什么、还没有防住什么，以及准备上线时必须做哪些事。专业术语后面尽量附上通俗解释。

## 先说结论

当前代码适合本地开发、内网试用和受控的单团队部署。它现在具备了第一层公网防护，但还不是可以让互不信任的公司或个人共同注册使用的 SaaS（多人在线服务）。

`AUTH_MODE=team` 已提供个人账号、服务端会话及负责人/编辑者/只读成员三种项目角色，接口会核对资源归属；平台管理员不自动获得项目数据权限。默认 `legacy` 仍是共享 Bearer Token（访问密钥）模式，拿到密钥的人可访问整个部署，不能用于区分多人身份。开通及账号恢复见[本地指南](./GETTING_STARTED.md#登录与团队开通)。目前仍缺企业登录、多重验证、组织级租户模型、完整负载和故障验收，不应视为成熟 SaaS。

## 已实现的第一层防护

| 防护                                     | 通俗解释                                | 当前行为                                                                                                        |
| ---------------------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| API Authentication（接口鉴权）           | 先验明“通行证”，再允许读取或修改数据    | team 模式核验个人会话及项目角色，公开接口仅限模式探测和登录；legacy 生产模式要求至少 32 字符的 `API_AUTH_TOKEN` |
| Constant-time comparison（恒定时间比较） | 避免攻击者根据比较耗时猜密钥            | 服务端比较的是两个 SHA-256 摘要，并使用恒定时间函数                                                             |
| Rate limiting（请求限流）                | 防止脚本短时间疯狂请求拖垮服务          | 全局默认每分钟 120 次；高成本诊断默认每分钟 10 次；健康检查不计数                                               |
| Body limit（请求体大小限制）             | 超大文件还没进入评测引擎就被挡住        | 默认最多 8 MiB，可配置但硬上限为 32 MiB                                                                         |
| Security headers（浏览器安全响应头）     | 告诉浏览器禁止部分危险行为              | 使用 Helmet 设置防嗅探、防嵌套等响应头；生产模式启用 HSTS                                                       |
| CORS allowlist（网页来源白名单）         | 只允许指定网页跨域调用接口              | 仅允许 `WEB_ORIGIN`，并只开放需要的方法和请求头                                                                 |
| Error boundary（错误边界）               | 用户看不到数据库、Python 进程或密钥细节 | 校验、限流、超大请求和内部错误均返回稳定的公开错误格式与请求编号                                                |
| Log redaction（日志脱敏）                | 日志中遇到密码、Token 等字段时替换掉    | API 与 Worker 日志对授权头、Cookie、密码、Token、API Key、连接字符串等常见敏感信息执行遮盖                      |
| Local-only data ports（数据端口仅本机）  | 局域网或公网不能直接连开发数据库        | Docker Compose 把 PostgreSQL 和 Redis 绑定在 `127.0.0.1`                                                        |
| Dependency scanning（依赖漏洞检查）      | 自动检查第三方包有没有公开漏洞          | CI 运行生产依赖审计；Dependabot 定期提升级 PR；CodeQL 扫描 TypeScript 和 Python                                 |

## 生产环境必填配置

不要直接复制示例密码。至少设置：

```dotenv
NODE_ENV=production
AUTH_MODE=team
API_DOCS_ENABLED=false
API_TRUST_PROXY=false
WEB_ORIGIN=https://你的网页域名
DATABASE_URL=postgres://独立低权限账号:强密码@数据库私网地址:5432/数据库名
DATABASE_SSL=true
REDIS_URL=rediss://独立账号:强密码@Redis私网地址:6379
MODEL_ENCRYPTION_KEY=<由密钥管理系统提供，不写入仓库>
```

`API_TRUST_PROXY`（信任反向代理）只有在 API 确实位于可信的 Nginx、Caddy、Cloudflare Tunnel 或云负载均衡器后面时才设为 `true`。错误开启会让攻击者伪造来源 IP，从而绕过按 IP 的限流。

先完成管理员初始化和项目归属迁移再启用团队模式。代理必须转发个人 `Authorization` 授权头，不能给所有人注入同一枚共享密钥。若保留 legacy 供受控单团队使用，生产环境还须配置至少 32 字符随机 `API_AUTH_TOKEN`。任何 Token 都不应写进 `VITE_...` 变量，Vite 会把它编译进公开网页。个人登录必须经过 HTTPS；内存令牌仍可能被 XSS（网页脚本注入）窃取，不能代替网页 CSP、依赖检查和 HTTPS。

`DATABASE_SSL=true` 使用 `verify-full`（完整证书与主机名校验），不只是把流量加密。数据库必须提供由系统信任的 CA（证书颁发机构）签发、且域名匹配的证书；不要通过关闭证书校验来绕过连接错误。

## 推荐上线拓扑

```text
Internet
   │ HTTPS（加密传输）
   ▼
CDN/WAF 或可信反向代理
   ├── 静态 Web 页面
   └── /api/* ──转发个人会话──▶ API
                                 ├── 私网 PostgreSQL
                                 ├── 私网 Redis ──▶ Worker
                                 └── 受限 Python Core
```

- WAF（Web 应用防火墙）负责挡住常见扫描和大流量攻击，但不能代替代码鉴权。
- PostgreSQL 与 Redis 不应有公网 IP；只允许 API/Worker 所在私网访问。
- API、Worker、Python 进程用非管理员账号运行，并限制 CPU、内存、进程数和磁盘。
- HTTPS 必须在可信代理终止；不要通过明文 HTTP 发送 Token、Prompt 或对话。

## 上线前检查单

- [ ] 所有示例密码均已替换，密钥只存在于部署平台的 Secret Manager（密钥保险箱）中。
- [ ] `.env`、数据库备份、评测数据和 Provider Key 从未提交到 Git。
- [ ] API 和 Worker 不以 root/Administrator 运行，数据库和 Redis 不开放公网端口。
- [ ] `WEB_ORIGIN` 是精确的 HTTPS 域名，不是 `*`。
- [ ] 反向代理限制请求大小和超时，应用层限制也保持开启。
- [ ] 根据预期并发调整限流；多副本部署时把限流计数迁移到共享 Redis。
- [ ] PostgreSQL 自动备份已开启，而且实际做过一次恢复演练。
- [ ] 日志、指标和报警能发现连续 401、429、500、任务积压和费用异常。
- [ ] 评测数据有保留期限和删除流程；敏感数据在发送模型厂商前完成脱敏。
- [ ] 在 GitHub Security 中启用 Secret Scanning、Push Protection、Dependabot Alerts 和 Code Scanning。
- [ ] 上线版本通过 `pnpm audit --prod --audit-level moderate`、全部测试和构建（中危及以上依赖告警阻止 CI 通过）。

## 当前仍未解决的上线风险

| 风险                                  | 为什么重要                                                 | 上线建议                                                                      |
| ------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 账号安全仍需增强                      | 个人会话及项目 RBAC 已实现，但没有 SSO/MFA/邮件验证        | 开放陌生人注册前补充企业登录、多重验证与账号风控；不要启用公开注册            |
| 项目隔离不等于组织级 Tenant Isolation | HTTP 已核验项目及关联资源归属，但尚无独立组织/计费模型     | 补组织边界、更多越权与并发测试、配额和隔离部署；不要宣称已支持公共多租户      |
| 原始 Bundle 与报告明文保存在数据库    | Prompt、输入、输出、评判理由可能很敏感                     | 使用云盘/数据库静态加密仍不够；还要做字段级加密、保留期限、删除和导出审计     |
| 单进程内存限流                        | API 扩为多个副本后，每个副本各算各的                       | 使用共享 Redis 限流，并让网关再做一层全局限流                                 |
| Python 插件不是安全沙箱               | 被批准加载的恶意插件仍可读文件和网络                       | 只加载审核过的插件；第三方插件放到独立容器/进程并设置只读文件系统和网络白名单 |
| 操作审计尚未覆盖全部读取与外部导出    | 账号、成员及部分业务操作有事件，但不等于完整合规审计       | 补审计检索、保留策略、防篡改存储和必要的访问事件                              |
| Provider 出站与费用控制仍需部署验收   | 已有地址限制、密钥加密和预估预算；预算不是供应商账单硬上限 | 配置精确供应商域名白名单、私网阻断与网关配额，验证 DNS/代理/超时和成本告警    |
| 缺少删除/合规工作流                   | 敏感对话可能保留过久                                       | 实现按项目的保留政策、软删除/硬删除、备份到期和删除证明                       |

真实服务链路、有界并发与故障恢复见[系统验收范围](./SYSTEM_TESTING.md)。受保护指标、隔离备份恢复、生产容器和 TLS 依赖已通过 CI，操作方式见[部署与备份恢复](./OPERATIONS.md)。这些检查尚未覆盖实际公网域名、告警接收、定时异地备份与生产容量；部署者需在实际环境逐项验收。
